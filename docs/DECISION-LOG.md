- 2026-10-19 — Contacts: the old lookup used SQL `LIKE %name%` and then "contains", so "Ma" matched every name containing "ma" and stopped as "more than one contact", while "Ma ❤️" never equalled "Ma". Matching now happens in Kotlin over all contacts with numbers using Unicode normalisation (emoji/punctuation as separators, accents folded for Latin only), exact → whole-word → near-spelling tiers; near spellings and several matches become a pick list that keeps the original call or message. Picking continues to the usual confirmation.

- 2026-10-19 — Alarm/timer cancellation: "cancel the alarm" used to fall into plan cancellation ("no active plans"). Clock commands are now parsed locally. Android has no API to list or cancel another app's alarms or running timers; JARVIS uses ACTION_DISMISS_ALARM / ACTION_DISMISS_TIMER, keeps its own record of what it set, verifies through AlarmManager's next alarm when possible, and otherwise says it cannot confirm and opens Clock. Device finding: Samsung Clock ignores ACTION_DISMISS_ALARM for upcoming alarms (it only opens the list). Rejected: scheduling JARVIS's own alarms (exact-alarm permission, ringing UI) for now.

- 2026-10-19 — Email drafting: the model filled the required `recipient_name` from context (an unrelated saved contact matched by "contains") and, told not to invent facts, wrote its questions into the subject and body. Email requests now run a structured dialogue (dates, reason, recipient for leave; content and recipient otherwise), asking only for what is missing; a model's `compose_email` arguments are not trusted for facts. The final text comes from a cloud model only if it keeps the user's dates and contains no placeholders; otherwise a deterministic writer composes it from the facts (offline-safe).

- 2026-10-19 — Voice: the "random" switch to the phone voice came from marking every answer that used a saved memory as private (private answers never go to ElevenLabs). Now only message/email content is private for the cloud voice (with a Settings option to allow it). The voice is chosen once per answer; ElevenLabs audio is received completely before playback and retried once on 429/5xx/network, so a failure moves the whole answer to the phone voice instead of finishing it in another voice. Spoken text is normalised separately from the written answer.

- 2026-10-19 — Voice conversations: an answer that asks a question is followed by one bounded listening session (on screen with the normal recogniser, in the background through the wake-word service, otherwise a "tap to answer" notification), at most four in a row. A Google-Assistant-style panel shows Listening (only while a recogniser is actually recording), Thinking, Speaking, and Stop. Background requests that need the screen now say why and post a notification that reopens JARVIS where the request waits, instead of a generic "Android blocks it".

- 2026-10-18 — Wake word now leads to a real interaction. Root cause of "it only shows a tap notification": on detection the service only set a UI flag that the Assistant tab consumed, and from the background it could do nothing but post a notification, because Android 10+ blocks starting an activity from the background (a microphone foreground service is not an exemption). Fix: `WakeCommandCoordinator` claims the mic, beeps, and captures the next request with SpeechRecognizer inside the service (allowed for a microphone foreground service), then hands the text to the live ViewModel, which runs it and reads the answer aloud even if auto-speak is off. If no JARVIS screen model is alive, a private "tap to run" notification carries the request. Requests that would open another app while no JARVIS screen is visible are parked behind a notification (`BackgroundHandoff`) instead of being reported as done. Also fixed: a busy retry loop when the microphone was unavailable (now backs off up to 10 s), the detector state is reset after each pause, and stopping the service always releases the mic. Considered and rejected: becoming the default assistant (VoiceInteractionService) and full-screen-intent or overlay tricks to bypass background-launch rules.
